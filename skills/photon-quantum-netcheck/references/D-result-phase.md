# D. 결과 (Result phase)

게임 종료 이벤트(`EventGameClearEvent` / `EventGameOverEvent` 등) 발화 후 결과 화면 표시 → 보상 처리 → 로비 복귀까지.

이 페이즈는 인게임만큼 네트워크 의존도가 높지 않지만, 두 가지 약점이 있음:
1. 보상은 서버 API 호출이 필요.
2. 양쪽이 동시에 결과 화면에 도달해야 통계가 어긋나지 않음.

---

## D1. 게임 종료 직후 한쪽 이탈

**발생 조건**
- 게임 종료 이벤트 발화 → 결과 화면 전환 중에 한쪽이 앱 종료.
- `OnPlayerLeftRoom` 발화.

**증상**
- 봇 활성화 트리거를 막아야 하는데 페이즈 분기가 잘못되어 있으면 결과 화면에서 봇이 활성화됨 (의미 없음).
- 또는 결과 화면 전환 자체가 실패.

**근본 원인**
- 페이즈 전환 타이밍 — 게임 종료 이벤트 직후 `EDisconnectPhase`가 `Gameplay` → `Result`로 안 바뀌었을 수 있음.
- 봇 활성화 핸들러가 페이즈를 안 보고 무조건 실행.

**대응**
- 게임 종료 이벤트 핸들러에서 **즉시** `_currentPhase = Result` 설정.
- `OnPlayerLeftRoom`에서 페이즈가 Result면 봇 활성화 skip.
- 결과 화면 진입은 로컬 처리 — 상대가 이탈해도 본인은 결과를 정상적으로 봐야 함.

**우선순위**: 中

---

## D2. 보상 ACK 누락 / 서버 API 실패

**발생 조건**
- 결과 화면에서 서버에 보상 지급 요청.
- 네트워크 지연 / 서버 5xx / timeout.

**증상**
- 사용자가 결과 화면에서 "보상 지급 중..." 무한 대기.
- 또는 사용자는 보상을 못 받았는데 서버엔 지급 처리된 race condition.

**근본 원인**
- 클라이언트가 idempotent하지 않은 호출을 함 (같은 보상을 두 번 요청).
- API timeout 후 retry 시 중복 지급 또는 양쪽 다 실패.

**대응**
- 보상 요청은 idempotency key (게임 세션 ID + 사용자 ID) 포함.
- timeout 6~10초 + 재시도 3회 (백오프).
- 모든 재시도 실패 시:
  - 클라이언트는 보상 미수령 상태로 표시.
  - 백그라운드로 재시도 큐에 적재 → 다음 앱 실행 시 다시 시도.
- 보상 지급 결과를 받기 전엔 "로비로" 버튼 비활성화 (사용자가 모르고 나가면 클레임 누락 가능).

**우선순위**: 高

---

## D3. 양쪽 결과 도달 타이밍 불일치

**발생 조건**
- 한쪽은 즉시 결과 화면, 다른 쪽은 frame 격차로 늦게 도달.

**증상**
- 빨리 도달한 쪽이 먼저 "다시하기" 또는 "로비로"를 누르고 방을 떠남.
- 늦게 도달한 쪽은 상대가 이미 사라진 상태로 결과 화면 진입.

**근본 원인**
- Quantum 결정론은 같은 frame에서 같은 상태를 보장하지만 **벽시계 시각**은 같지 않음.
- 결과 화면 UI는 프레임 단위 동기화 대상이 아님 (Quantum 외부).

**대응**
- 결과 화면 도달 시 본인이 "result_arrived = true" CustomPlayerProperty 셋팅.
- 양쪽 모두 도달했을 때 다음 단계(보상 지급, 통계 송신) 진행.
- 한쪽이 미도달인 상태로 일정 시간(10초) 초과 시 본인만 진행.
- UI: 상대가 결과 화면 도달 안 한 동안 "상대 결과 대기 중..." 표시. 단, 게임 자체는 끝났으므로 잠금 강제는 안 함.

**우선순위**: 低

---

## D4. 분석 사유 분류 (텔레메트리)

**발생 조건**
- 게임 종료 / 매칭 실패 / 재접속 실패 등 다양한 종료 경로를 텔레메트리에 기록.
- 모든 실패를 "fail" 한 가지 사유로 묶음.

**증상**
- 사후 분석할 때 게임 조건(체력 소진 등) 패배인지, 재접속 timeout 초과 실패인지, 매칭 실패인지 구분 불가.
- 어디서 사용자 이탈이 많이 발생하는지 파악 불가.
- A/B 테스트 결과 해석 어려움.

**근본 원인**
- 종료 경로마다 같은 "fail" 이벤트만 송신.
- 사유 필드(`fail_reason`) 가 없거나 항상 같은 값.

**대응**
- 종료 경로마다 사유 enum 분리:

| 사유 | 발생 경로 |
|------|----------|
| `GameConditionLost` | 게임 조건(체력 소진/스코어 차이 등)으로 정상 패배 |
| `ReconnectTimeout` | 로컬 재접속 grace timeout 초과 후 결과 화면 |
| `OpponentLeft` | 상대 이탈 + 대체 세션으로 진행 → 패배 |
| `MatchFailed` | 매칭 자체 실패 (서버 입장 실패, 사용자 취소 등) |
| `BackgroundExceeded` | 백그라운드 grace 초과로 강제 종료 |
| `ChecksumError` | Quantum desync 감지 |
| `RuntimeConfigBuildFailed` | 시작 직전 데이터 빌드 실패 |
| `AppForceKill` | 앱 강제 종료 (재실행 시 서버 조회로 회수) |
| `Victory` | 정상 승리 |

- 결과 팝업 분기와 텔레메트리 이벤트 둘 다 같은 enum 사용.
- 대체 세션 진입 경로도 분류: `ReplacementFromStart` (매칭 자체가 대체 세션), `ReplacementMidMatch` (중도 상대 이탈), `ReplacementMatchFailed` (매칭 실패 fallback).
- 사유별 fail_count 대시보드 → 어떤 경로가 가장 빈도 높은지 모니터링.
- 결과 팝업 표시 후 사유 플래그 리셋 (다음 결과 화면에 잘못 이월되지 않도록).

**우선순위**: 中
