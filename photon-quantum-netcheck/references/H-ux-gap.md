# H. UX gap (조용히 실패하는 케이스)

시스템 동작은 있지만 사용자에게 노출되는 UI/피드백이 없어 "그냥 멈춘 것처럼" 보이는 케이스들. 다른 카테고리(A~G)에서 다룬 시나리오 중에서도 UX 약점이 있는 항목들을 한 곳에 모았다.

진단 시 가장 놓치기 쉬운 영역 — 코드 동작은 맞지만 사용자 경험이 깨진 경우.

---

## H1. 재접속 30s 타이머 — 전용 오버레이 UI 없음

**발생 조건**
- 인게임 중 끊김 → C2 로컬 재접속 타이머 작동.
- 이벤트(`OnLocalDisconnected`)는 발화되지만 구독하는 UI 없음.

**증상**
- 사용자 화면은 멈춘 채로 30s 동안 아무 변화 없음.
- 사용자가 "버그"로 인식하고 강제 종료 → 30s 대기 의미 없어짐.
- 30s 후 갑자기 결과 화면 표시 (사용자는 영문 모름).

**근본 원인**
- 백엔드 로직(타이머/재접속 시도)은 구현되어 있는데 프론트 UI 컴포넌트가 연결 안 됨.
- "이벤트가 있는데 구독하는 곳이 없는" 전형적인 케이스.

**대응**
- 전용 오버레이 컴포넌트 (`UI_ReconnectOverlay`) 만들기:
  - "재연결 시도 중..." 메시지
  - 남은 시간 카운트다운 (XX초)
  - 취소 버튼 (선택적 — 즉시 패배 처리)
- `OnLocalDisconnected` / `OnLocalReconnectTimer` / `OnLocalReconnectFailed` / `OnLocalReconnectSucceeded` 이벤트를 모두 구독.
- 진단 시 "이벤트는 발화하는데 구독자가 없음" 패턴을 grep으로 찾을 수 있도록 일관된 명명 규칙(`On*` 이벤트 + `Subscribe`).

**우선순위**: 高

## H2. 매칭 대기 중 상대만 이탈 — 사용자 피드백 없음

**발생 조건**
- 매칭 대기 중 상대가 잠깐 들어왔다 나감.
- 또는 직전 상대 rematch 회피로 silent 재매칭 발생.

**증상**
- 매칭 화면이 그대로 — "상대 취소" 같은 문구 없음.
- 사용자는 단지 매칭이 길어진다고 느낌.

**근본 원인**
- 시스템 동작은 정상 (타이머 계속, 자동 재시도) 이지만 사용자에게 무슨 일이 일어났는지 안 보임.
- "조용히 동작"이 의도된 설계일 수도 있음 — 정책 결정 필요.

**대응**
- 정책 옵션:
  - **옵션 A (조용히)**: 별도 UI 없이 타이머만 계속. 사용자 혼란 최소화 (현재 흔한 선택).
  - **옵션 B (피드백 있음)**: "다른 상대를 찾고 있습니다" 같은 약한 피드백.
- 옵션 A를 선택한다면 의도적임을 코드 주석 + 문서로 명시 → 향후 누군가 "왜 UI 없지?" 라고 다시 검토하지 않게.
- 어느 옵션이든 진행 표시(스피너, 점선 등)는 유지 — 완전히 정지된 화면은 피하기.

**우선순위**: 中

## H3. 시뮬 desync (체크섬 불일치) — 로그만 남음

**발생 조건**
- Quantum `CallbackChecksumErrorFrameDump` 발화.
- C4에서 다룬 케이스의 UX 측면.

**증상**
- 양쪽 화면이 다르게 진행 (desync 상태).
- 사용자는 "왜 적이 한쪽에선 죽었는데 다른 쪽에선 살아있지?" 혼란.
- 로그만 남고 강제 종료 / 안내 없음.

**근본 원인**
- desync는 결정론 깨짐 — 자동 복구가 어려움.
- 강제 종료/재시도 UI를 만들지 않으면 사용자는 끝까지 desync 상태로 진행.

**대응**
- 즉시 처리:
  - desync 감지 시 "동기화 오류가 발생했습니다" 모달 + "결과 화면으로" 버튼.
  - 또는 자동으로 게임 강제 종료 → D4의 `ChecksumError` 사유로 결과 처리.
- 텔레메트리는 필수 — desync 빈도 모니터링 (C4 참조).
- 사용자 신뢰 보호: desync 발생 시 양쪽 모두 "비정상 종료"로 분류 → 패배 처리 안 함 (또는 양쪽 무승부).

**우선순위**: 高

## H4. 인게임 명령 전송 실패 — 입력이 안 먹는 것처럼 보임

**발생 조건**
- Quantum Command 송신 실패 (C9). 시뮬 세션 없음 / 관전 상태 / 용량 초과 등.

**증상**
- 사용자 입력(게임 액션 — 유닛 배치/이동/스킬/공격 등) 후 게임 화면에 반영 안 됨.
- 다시 시도해도 안 됨 → "버그"로 인식.
- 에러 로그만 남음.

**근본 원인**
- Command 전송은 deterministic input이라 실패해도 시뮬에 영향 없지만, 사용자는 그게 정상 처리됐는지 모름.
- 실패 시 자동 재시도 / 사용자 알림 없음.

**대응**
- Command 송신 실패 시:
  - 1~2회 자동 재시도 (지수 백오프).
  - 그래도 실패 시 사용자에게 토스트 ("입력 처리 실패. 다시 시도해주세요").
- 클라이언트 사이드에서 입력을 미리 표시(predicted) → Verified 도달 시점에 정정. 사용자가 즉시 피드백 받을 수 있음.
- 송신 실패가 일정 빈도 이상이면 텔레메트리로 추적.

**우선순위**: 中

## H5. 상대 프로필 무한 대기 — B10의 UX 면

**발생 조건**
- B10 케이스 — 상대 프로필이 안 옴 + timeout 없음.

**증상**
- "상대 로딩 중" 문구가 영원히 표시.
- 사용자는 어디서 멈췄는지 모름.

**근본 원인**
- B10 참조. 본 항목은 UX 측면 강조.

**대응**
- B10의 timeout 설정에 더해, 대기 시간 길어질수록 사용자에게 단계별 피드백:
  - 0~5s: "상대 로딩 중..."
  - 5~15s: "상대 데이터 동기화 중..."
  - 15s+: "연결이 느립니다" + 취소 버튼 노출
- 사용자가 직접 취소할 수 있는 출구를 제공 → "버그로 멈춤" 인식 방지.

**우선순위**: 中

## H6. silent retry / rematch — 진행 표시 없음

**발생 조건**
- 직전 상대 회피 rematch (A9) — silent하게 3회 재시도.
- 동시 매칭 사후 복구 (A11) — silent하게 1회 재시도.
- AI 프로필 API 재시도 (B8) — silent하게 3회 재시도.

**증상**
- 사용자 화면은 그대로 "매칭 중" → 시간만 지남.
- 어느 단계에서 멈췄는지 사용자가 알 수 없음.

**근본 원인**
- silent는 의도된 설계 — UX 단순화 목적.
- 하지만 사용자에게 진행감이 없으면 "응답 없음"으로 보임.

**대응**
- 어떤 retry든 사용자 화면에는 **진행 표시(스피너/점선/도트 애니메이션)** 항상 유지.
- 백엔드 로그는 retry 단계마다 명시적 분기 — 진단 시 어느 단계에서 막혔는지 확인 가능.
- 누적 대기 시간이 임계(예: 20s) 초과하면 약한 텍스트 변화 ("매칭이 평소보다 오래 걸립니다").
- 텔레메트리: silent retry 단계마다 이벤트 → "어디서 retry가 자주 발생하는지" 모니터링.

**우선순위**: 中
