# G. 매칭 진입 전 (Pre-match)

사용자가 매칭 버튼을 누른 직후, 아직 Photon 연결을 시작하기 전에 통과해야 하는 검사들. 이 단계에서 거른 케이스는 Photon에 접속조차 하지 않으므로 매칭 풀이 더 깔끔해진다.

> 이 카테고리는 게임 정책에 따라 선택적으로 적용된다. 예를 들어 자원(에너지/스태미너) 시스템이 없는 게임은 G1의 자원 검사를 skip.

---

## G1. 사전 검사 (에너지/스태미너 / 앱 버전 / 시즌 데이터)

**발생 조건**
- 사용자가 매칭 시작 버튼을 누름.
- 게임 정책상 필요한 리소스/조건을 검사해야 함.

**증상**
- 검사 누락 시:
  - 에너지가 0인데 매칭이 시작되어 게임 끝까지 진행 (정책 위반).
  - 구버전 앱이 신버전 클라이언트와 매칭 → 결정론 깨짐 (F2 참조).
  - 시즌 데이터가 안 받아진 상태로 매칭 → RuntimeConfig 빌드 실패 (B5).

**근본 원인**
- 매칭 시작 함수가 바로 `ConnectToRoomAsync`로 직행.
- 사전 검사는 다른 곳(UI 버튼 활성 조건 등)에만 있어 race로 우회 가능.

**대응**
- 매칭 시작 함수 진입 시점에 검사 체인:

| 검사 | 실패 시 동작 | 적용 게임 |
|------|--------------|----------|
| 자원(스태미너/에너지/티켓 등) 부족 | 안내 + 충전/획득 안내, 매칭 시작 안 함 | 자원 시스템 채택 게임 |
| 앱·콘텐츠 버전 (서버 조회) | 강제 업데이트 팝업 | 모든 게임 |
| 시즌/이벤트 데이터 로드됨 | 기본값으로 진행 또는 재로드 후 재시도 | 시즌제 게임 |
| 초대 코드 비어 있음 (코드 입장만) | 입력 안내 | 코드 입장 지원 게임 |
| 닉네임 / 프로필 설정 완료 | 초기 설정 화면으로 강제 이동 | 닉네임 필수 게임 |

- 검사는 동기/순차 — 첫 실패 즉시 return, 다음 검사 안 함.
- 각 실패엔 별도 텔레메트리 이벤트 (어떤 검사에서 막혔는지 추적).
- 사전 검사 실패 시 Photon 연결 자체를 시도하지 않음.

**우선순위**: 高

## G2. 자원 차감 시점 (에너지/티켓 등)

> 매칭 진입에 자원 차감 정책이 있는 게임에만 해당.

**발생 조건**
- 매칭 진입 비용으로 자원(에너지/티켓/입장권 등)을 차감해야 함.
- 차감 시점을 잘못 잡으면 매칭 실패/취소 시 사용자 손실 발생.

**증상**
- 매칭 직후 차감 → 매칭 실패 / 사용자 취소 시 환불 처리 누락 → 손실 클레임.
- 매칭 성공 후 게임 시작 직전 차감 → 차감 직전 끊김 시 무료 게임 발생.
- 차감과 게임 시작이 비동기인 경우 race window.

**근본 원인**
- 차감 → 매칭 → 게임 시작 흐름에 명확한 commit point가 없음.
- 환불 로직 없거나 idempotent하지 않음.

**대응**
- 차감 시점은 **양쪽 모두 게임 씬으로 넘어가기로 확정된 순간** — 권장:
  - Photon 매칭 성사
  - 양쪽 ready 신호 교환 완료
  - 씬 전환 직전
- 그 전에 취소/실패한 경우 차감 안 함.
- 차감 후 게임 시작 실패(B4, B5) 케이스를 위해 idempotency key 기반 환불 API 준비.
- 차감 호출은 서버 단일 트랜잭션 — 클라이언트는 결과만 받음 (이중 차감 방지).
- 텔레메트리: 차감 / 환불 / 실패 이벤트 분리.

**우선순위**: 中

## G3. 닉네임 / 사용자 텍스트 sanitization

**발생 조건**
- 사용자 닉네임을 Photon CustomPlayerProperty로 송신.
- 닉네임에 `\`, 줄바꿈, null 문자, 제어 문자 등이 포함될 수 있음 (이모지 가능 환경에 따라 다름).

**증상**
- 일부 클라이언트에서 닉네임이 깨져 표시.
- 직렬화/역직렬화 시 문자열 파싱 실패 → 매칭이 끊김.
- 텍스트 렌더링 도중 게임 멈춤 (TMP_Text 등이 제어 문자에 취약).
- 보안 이슈 (XSS 흉내, 로깅 인젝션).

**근본 원인**
- 닉네임을 raw하게 그대로 송신.
- Photon은 string을 단순히 byte로 전송 — 받는 쪽 클라이언트가 안전하게 처리해야 함.

**대응**
- 송신 직전 sanitize:
  ```csharp
  string SanitizeNickname(string raw) {
      if (string.IsNullOrEmpty(raw)) return "Player";
      // 제어 문자 제거
      var cleaned = new string(raw.Where(c => !char.IsControl(c)).ToArray());
      // 줄바꿈, 백슬래시 등 깨지는 문자 제거
      cleaned = cleaned.Replace("\\", "").Replace("\n", "").Replace("\r", "");
      // 길이 제한
      if (cleaned.Length > 16) cleaned = cleaned.Substring(0, 16);
      return string.IsNullOrEmpty(cleaned) ? "Player" : cleaned;
  }
  ```
- 받는 쪽에서도 한 번 더 검증 — 신뢰하지 말 것.
- 닉네임 외에도 사용자 입력 텍스트(채팅 등)는 모두 sanitize.

**우선순위**: 中

## G4. 매칭 진입 mutex / 중복 클릭 방지

**발생 조건**
- 사용자가 매칭 시작 버튼을 연타.
- 또는 UI 애니메이션 중에 매칭 시작 함수가 여러 번 호출됨.

**증상**
- 매칭이 두 번 시도되어 Photon state가 꼬임.
- "이미 연결 중" 예외 발생.
- 두 번째 호출이 첫 번째를 cancel하면서 race condition.

**근본 원인**
- 매칭 시작 함수에 mutex/lock 없음.
- 버튼 onClick에 비활성 처리 누락.

**대응**
- 매칭 시작 진입 시점에 `_isStartingMatch` 플래그 확인:
  ```csharp
  if (_isStartingMatch) return;
  _isStartingMatch = true;
  try { /* match logic */ }
  finally { _isStartingMatch = false; }
  ```
- 매칭 버튼은 클릭 직후 즉시 `interactable = false` → 매칭 완료/실패 후 다시 활성화.
- A10(매칭 취소 후 즉시 재시작 race)과 짝 — disconnect 진행 중에도 새 매칭 시도 차단.

**우선순위**: 中
